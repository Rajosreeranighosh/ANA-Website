Engineering overview

Architecture, without the hype.

A plain-language view of the ANA prototype: what the codebase is working on, what is still experimental, and what must be proven before a public network launch.

Prototype status: ANA is not a production blockchain or mainnet. The descriptions below are engineering context, not guarantees of security, decentralization, uptime, or token value.

Current building blocks

Proof of work

RandomX and Rust

The project explores CPU-oriented RandomX proof of work in a Rust node implementation. Mining support alone does not establish a secure, fully validated consensus network.

Node state

Persistent local state

The development node includes persistent state handling. A production-grade canonical chain database, recovery guarantees, and independently validated public chain data still need to be demonstrated.

Peer communication

Authenticated transport

Mutual TLS 1.3 peer transport is being developed in draft PR #41. It remains unmerged and requires passing cross-platform CI and security review.

Internal protocol

Node request handling

The node development branch includes an authenticated TCP request protocol for internal node communication and queries. It is not a public browser-facing HTTP API and should not be exposed directly to website visitors.

What is not ready yet

  • A public, monitored testnet endpoint with stable availability and operational ownership.
  • A documented, read-only HTTP API or secure gateway for explorer queries.
  • End-to-end multi-node synchronization tests and adversarial consensus testing.
  • Demonstrated enforcement of the proposed 21,000,000 ANA supply limit under all valid chain transitions.
  • Independent security review, incident response procedures, and production deployment controls.

Security boundary for the website

A browser must never receive node private keys, peer certificates, node authentication tokens, or privileged peer-network credentials. The future explorer should query a narrowly scoped read-only service that validates data against canonical node state, applies strict rate and input limits, and exposes only public information.

Development checkpoints

Checkpoint 1

Finish peer transport tests

Pass Windows and Ubuntu CI, resolve findings, and obtain a focused security review before merge.

Checkpoint 2

Prove consensus and supply rules

Test invalid blocks, reorg behavior, issuance boundaries, and multi-node agreement.

Checkpoint 3

Publish a safe read API

Define stable schemas, pagination, access controls, and integration tests before building live explorer features.

Checkpoint 4

Operate a monitored testnet

Only then publish verified network metrics and connect the website explorer to a known endpoint.
